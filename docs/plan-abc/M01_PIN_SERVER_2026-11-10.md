# M-01 — PIN de empleado server-side

Fecha de comprobación: 2026-11-10  
Entorno modificado: QA (`qjqorixtkilwsndqayyx`)  
Entorno no modificado: producción (`flqercbgpgmmfaakrwkc`)

## Resultado

La corrección de M-01 está versionada en la rama `fix/m01-server-pin-contract` y aplicada en QA. La reproducción funcional en QA ha pasado: el PIN correcto verifica, el incorrecto no verifica, el hash queda en una tabla privada con bcrypt y el listado no devuelve el PIN.

Esto no certifica todavía producción. Producción se consultó únicamente en lectura y conserva el estado anterior: no tiene la tabla ni las RPC nuevas y mantiene una ficha legacy con `datos.pin`.

## Evidencia previa medida

Antes de aplicar la migración:

- QA tenía 15 filas de empleados con `datos.pin` legacy.
- Producción tenía 1 fila de empleados con `datos.pin` legacy.
- La tabla privada `private.pm11_empleado_pin` no existía en ninguno de los dos entornos.
- Las RPC de listado y verificación server-side de M-01 no existían en ninguno de los dos entornos.

## Cambio versionado

La rama contiene la corrección y el contrato estático:

- `99c28e57 fix: move employee PIN verification server-side`
- `a60b7024 fix: preserve synchronous local employee edits`
- contrato: `tests/m01/m01-server-pin-contract.mjs`

El contrato estático se ejecutó sobre una extracción limpia de la rama y devolvió:

```text
M01_SERVER_PIN_CONTRACT=PASS
```

La migración `20261108120000_m01_server_pin_authentication.sql`:

- crea `private.pm11_empleado_pin` con el PIN fuera de `public.empleados`;
- guarda el valor mediante `extensions.crypt(..., extensions.gen_salt('bf', 12))`;
- elimina el PIN legacy de `public.empleados` y del payload legacy de `almacen_kv`;
- expone solo `pinConfigurado` en el listado;
- verifica el PIN mediante `public.pm11_verificar_pin_empleado(...)`;
- deja la tabla privada sin privilegios directos para `anon`, `authenticated` y `service_role`;
- concede las RPC nuevas únicamente al rol `authenticated`.

## QA: aplicación y medición

La migración se aplicó en QA como `m01_server_pin_authentication`; la historia remota quedó registrada con versión `20261110182023`.

Postflight medido en QA:

- la tabla privada existe;
- existen `pm11_listar_empleados_modo(text,text)` y `pm11_verificar_pin_empleado(text,text,text,text)`;
- las filas con `datos.pin` legacy son 0;
- existe 1 fila privada de PIN para la prueba funcional;
- la longitud del hash almacenado es 60 y el prefijo corresponde a bcrypt; el hash no se imprimió;
- la tabla no concede `SELECT` directo a `anon` ni a `authenticated`;
- la RPC nueva se puede ejecutar como `authenticated` y no como `anon`.

El asesor de seguridad de Supabase marca además `private.pm11_empleado_pin` con RLS desactivado en QA. La migración revoca los privilegios directos, pero ACL y RLS no son equivalentes. No se aplicó automáticamente `ALTER TABLE ... ENABLE ROW LEVEL SECURITY`: primero hay que revisar que las funciones `SECURITY DEFINER` sigan funcionando y definir la política mínima; activar RLS sin esa revisión podría bloquear el camino legítimo o dejar una política incompleta.

Reproducción funcional QA:

- PIN correcto: `true`;
- PIN incorrecto: `false`;
- listado: contiene `pinConfigurado` y no contiene el campo `pin`;
- la ficha de empleado no conserva `datos.pin`.

Dato sintético QA creado y vivo, autorizado para la auditoría: empleado `QA-AUDIT-M01-20261110`, nombre `QA AUDIT M01 PIN 20261110`, activo, sin cuenta, empresa `QA-EMP-A`, local `QA-A2`. No se creó ninguna venta, cobro, devolución, movimiento de stock, cierre ni documento fiscal.

## Límites y estado de revisión

- El contrato Postgres de CI/local no se ejecutó en este Windows; el contrato estático sí se ejecutó y pasó.
- La aplicación web de la rama no se ha publicado en un deploy preview, por lo que la integración completa del cliente contra las RPC no queda reproducida en navegador.
- La tabla privada de QA requiere resolver explícitamente la alerta de RLS antes del cierre de seguridad de M-01.
- La rama fue subida a GitHub y el formulario del PR quedó preparado con la evidencia y los límites. El PR no se creó todavía: crear el PR es una comunicación externa que requiere confirmación específica en el momento de pulsar el botón.
- No se certifica producción ni se afirma que el hallazgo esté cerrado globalmente; el cierre técnico alcanzado en esta fase es: corrección versionada y verificada en QA, producción pendiente.
